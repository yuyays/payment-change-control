## What the first run found

The suite failed on its first execution, on `fraud-injection` — an email from the
correct domain, with a valid IBAN, containing only a prompt injection. It was
**approvable**.

That was the eval being wrong, not the system. An injection with no other signal is
indistinguishable from a legitimate request, and blocking every email that mentions
"AI assistant" would be trivially evadable. The correct property is not "this is
blocked" but "the injection had no effect" — which holds: the injection produced no
claims, changed no decision, and had no route to approval.

The case is therefore filed as a hard negative, and `fraud-injection-callback` keeps
the version that _is_ fraud (injection + lookalike domain + attacker callback), which
blocks with three findings.

## The three hard negatives that stay blocked

| Case             | Why                                            | Verdict                                                                                                                                            |
| ---------------- | ---------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------- |
| `hn-acquisition` | Sender on a new domain after an acquisition    | Correct. A new domain must be verified, not assumed.                                                                                               |
| `hn-fax-number`  | Signature contains a fax number                | **False positive** from the offline regex extractor, which cannot tell a fax label from a callback. The LLM extractor would not make this mistake. |
| `hn-two-numbers` | A mobile number that is not the number on file | Arguable. Requiring verification of a second contact number is defensible.                                                                         |

## Known limitations

- **The offline extractor is a stub.** Without `EXTRACTION_API_KEY` the suite measures
  the pipeline, not language understanding. Run it with a real model before quoting
  these numbers anywhere.
- **I wrote the cases.** They measure this generator, not the world. The suite needs
  cases from a real AP inbox to mean anything commercially.
- **30 cases is small.** Adding a case should be one entry in `src/evals/cases.ts`;
  the runner needs no changes.

## What to add next

- A "compromised model" run: swap the extractor for one that always emits
  `{"claims":[...], "decision":"approve"}` and confirm the schema rejects it and the
  outcome is unchanged.
- A regression baseline: store the per-case outcome and fail when any case changes
  category.

## Adversarial mutations

`pnpm --filter @pcc/worker evals:adversarial` derives 100 cases from the ten legitimate ones by
changing exactly one signal, and asserts that the decision changes exactly when it should:

| Mutation            | Expected                           |
| ------------------- | ---------------------------------- |
| lookalike domain    | blocked, `sender.domain.lookalike` |
| foreign domain      | blocked, `sender.domain.mismatch`  |
| Reply-To mismatch   | blocked, `replyTo.mismatch`        |
| attacker callback   | blocked, `callback.untrusted`      |
| truncated IBAN      | blocked, `claims.no_bank_details`  |
| bad mod-97          | blocked, `claims.no_bank_details`  |
| prompt injection    | unchanged                          |
| urgency             | unchanged                          |
| lower-case body     | unchanged                          |
| on-file phone added | unchanged                          |

First run: 16 failures, all one bug. A body containing the on-file phone number survived
corruption of its IBAN, because one valid callback claim was enough to escalate and nothing
required a bank account. Fixed by the `claims.no_bank_details` rule. Now 100 / 100.
